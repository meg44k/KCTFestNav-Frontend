# 管理コンソール 設計

- 作成日: 2026-10-05
- 対象リポジトリ: KCTFestNav-Frontend（画面）、KCTFestNav-Backend（API の追加・修正）
- 期限: 高専祭（2026-10-31〜11-01）の 1 週間前、**10/24 までに担当者へ配布できる状態**

## 1. 目的

来場者向けの画面はあるが、データを更新する手段が API しかない。
運営側の 3 種類の利用者が、ブラウザ（主にスマホ）から必要な操作だけをできるようにする。

| 利用者 | ロール | いつ・どこで | 主な操作 |
|---|---|---|---|
| 管理者 | `Admin` | 祭の前、PC | ブースの登録、担当者アカウントの発行 |
| 学生会 | `Gakuseikai` | 当日、スマホ/PC | ライブの切り替え、お知らせ、全ブースの監視 |
| 企画担当 | `Student` | 当日、スマホ、忙しい合間 | 自分のブースの混雑度の更新 |

成功の基準:
- 企画担当がログイン済みのスマホから **1 タップ**で混雑度を変えられる
- 学生会が、混雑度を長く更新していないブースに気づける
- 管理者が、全ブースの担当者アカウントを一度に発行し、配布用の一覧を得られる

## 2. 決定事項（本人と合意済み）

- 管理画面は既存フロント（Next.js）の `/manage` 以下に作る。別アプリにはしない
- 企画担当のアカウントは **ブースごとに 1 つ**を担当者全員で共有する（誰が更新したかは追わない）
- ログイン状態は **Next.js のサーバー側で JWT を httpOnly Cookie に保存**する。API はすべてサーバー側（Server Component / Server Action）から呼ぶ。
  理由: フロントは HTTPS、API は http のため、ブラウザから直接呼ぶと mixed content で遮断される（来場者向けページと同じ方式）
- UI は来場者向け画面の雰囲気に合わせる（§4）
- 段階 0 → 1 → 2 → 3 の順に作り、段階ごとに PR を出す

## 3. 段階と予定

| 段階 | 期限 | 内容 |
|---|---|---|
| 0 土台 | 10/11 | ログイン、ロールごとの振り分け、共通レイアウト、API 呼び出しの仕組み、権限の穴の修正 |
| 1 管理者 | 10/17 | ブースの一覧・登録・編集・削除、アカウントの一括発行と再発行 |
| 2 企画担当 | 10/22 | 混雑度のワンタップ更新、最終更新時刻、ブース説明の編集 |
| 3 学生会 | 10/24 | ライブの状態切り替え、お知らせの更新、混雑度の監視 |
| 4 発展 | 余裕があれば | 変更履歴、QR ログイン、売り切れ表示、3D の棟・階の割り当て |

段階 4 はこの設計の対象外。必要になったら別に設計する。

## 4. UI の方針

来場者向け画面（`class-booth`, `bazaar` など）に合わせる。

- 黒背景・白文字（`globals.css` の `--background` / `--foreground`）、フォントは Zen Kaku Gothic New
- 見出しは `font-extrabold`、中央寄せ
- 混雑度の色は来場者画面と同じ: 空き `#00B894`、少し混雑 `#FDCB6E`、非常に混雑 `#e54141`
- 部品は既存の shadcn/ui（`button`, `dialog`, `badge`, `drawer`）を使う。足りない入力部品（`input`, `textarea`, `label`）は shadcn から追加する
- モバイルファースト。企画担当と学生会の画面は片手で押せる大きさ（ボタンの高さ 56px 以上）。管理者の画面は PC でも見やすい幅で表示する

## 5. 段階 0: 土台

### 5.1 画面

| パス | 内容 |
|---|---|
| `/manage/login` | ログイン ID とパスワードの入力のみ。失敗時は「ID かパスワードが違います」 |
| `/manage` | ログイン後の振り分け。Admin → `/manage/booths`、Gakuseikai → `/manage/ops`、Student → `/manage/my-booth`、Member → 「管理画面の権限がありません」とログアウトボタン |
| `/manage/booths` ほか | 段階 0 では「準備中」の空ページ |

共通レイアウト（`/manage/login` 以外）:
- 上部にログイン中のユーザー名とログアウトボタン
- Admin と Gakuseikai には、使える画面へのメニュー（Admin は全画面、Gakuseikai は `/manage/ops` のみ）
- Student にはメニューを出さない（使う画面が 1 つのため）
- 来場者向けの `SideMenu` は出さない

### 5.2 仕組み

- `src/app/actions/auth.ts`
  - `loginAction`: `POST /auth/login` を呼び、返った JWT を Cookie `kct_manage_token` に保存して `/manage` へリダイレクト。
    Cookie は `httpOnly`, `secure`, `sameSite: "lax"`, `path: "/manage"`, 有効期限は JWT と同じ 72 時間
  - `logoutAction`: Cookie を消して `/manage/login` へ
- `src/proxy.ts`（Next.js 16 で middleware から改名）
  - `/manage/*`（`/manage/login` を除く）で Cookie が無ければ `/manage/login` へリダイレクトする。
    ここは振り分けだけで、権限の判断はしない（Next.js のドキュメントの推奨どおり）
- `src/lib/api/manage.ts`
  - `manageFetch(path, init)`: Cookie の JWT を `Authorization: Bearer` で付けて既存の `apiFetch` を呼ぶ
  - 401 のとき: Cookie を消して `/manage/login` へリダイレクト
  - 403 のとき: 呼び出し元に権限エラーとして返す（画面で「権限がありません」と表示）
- ロールの判定: レイアウトで `GET /auth/me` を呼び、その結果で表示を切り替える。JWT をフロントで検証したり解読したりはしない
- 各画面の本当の権限チェックはバックエンドが行う（`docs/permissions.md` のとおり）。フロントの振り分けは見た目の都合

### 5.3 バックエンドの修正

ブランチ `feature/manage-auth-fix`（KCTFestNav-Backend）。

- `GET /manage/users/:id`（`UserUsecase.GetByID`）に Admin チェックが無いので追加する（`Create` と `GetAll` には既にある）
- `docs/permissions.md` を現在の実装に合わせて直す（ユーザーの作成・一覧が Admin 限定になっていることを反映）

### 5.4 テスト

- フロント（vitest）: `manageFetch` が 401/403 で正しく振る舞うこと、ロールからリダイレクト先を決める関数
- バックエンド: Admin 以外が `GetByID` で拒否されるテスト
- 手動: ローカルでバックエンドを起動し、ロールごとのアカウントでログイン → 振り分け → ログアウトを確認

## 6. 段階 1: 管理者（Admin）

### 6.1 ブース管理 `/manage/booths`

- 一覧: 名前、主催者、場所、混雑度、担当アカウントの有無。PC では表、スマホではカード
- 登録・編集（ダイアログ）: 名前、主催者、説明、場所（自由記述）、画像 URL、緯度、経度
  - `x`, `y`, `z` は DB では必須だが現在どこでも使っていないため、画面では出さず 0 を送る
  - 画像はアップロードではなく URL の入力にする（アップロード先が無いため）
  - 緯度・経度は数値入力。来場者画面のコンパスナビで使う
- 削除: 確認ダイアログを出してから `DELETE /manage/booths/:id`。担当アカウントは DB の設定により担当ブースが空になるだけで残る

### 6.2 アカウント発行 `/manage/accounts`

> 2026-10-05 追記: バックエンドの `PUT /manage/users/:id` は受け取ったパスワードをハッシュ化せずにそのまま保存しており、
> 更新後はログインできなくなる。パスワード再発行の前提として、段階1でバックエンドを直す
> （パスワードが空なら今のハッシュを保つ、空でなければハッシュ化して保存する）。

ブースごとに 1 アカウントなので、CSV の取り込みではなく「ブース一覧から発行する」形にする。

- 「未発行のブースにまとめて発行」ボタン: 担当アカウントの無いブースすべてに Student アカウントを作る
  - ログイン ID: `booth-<ブースID>`（例: `booth-12`）
  - パスワード: ランダムな 10 文字（紛らわしい `0/O/1/l/I` を除いた英数字）
  - 名前: ブースの主催者名
- 発行直後に、ブース名・ログイン ID・パスワードの一覧を表示する。**パスワードはこの画面でしか見られない**（バックエンドはハッシュで保存しているため）。
  一覧は印刷用の表示と、CSV のダウンロードができる
- 個別の「パスワード再発行」: 新しいパスワードを作って `PUT /manage/users/:id` で更新し、その場で表示する
- 学生会のアカウントは同じ画面の「アカウントを追加」から、ロールを Gakuseikai にして個別に作る
- アカウント一覧は `GET /manage/users` から作り、担当ブースで並べる

## 7. 段階 2: 企画担当（Student）

### 7.1 自分のブース `/manage/my-booth`

- 担当ブースは `GET /auth/me` の担当ブース ID から取る
- 画面の上半分に混雑度のボタンを 3 つ縦に並べる（空き／少し混雑／非常に混雑、来場者画面と同じ色）。
  押すと即座に `PATCH /manage/booths/:id/congestion` を呼び、現在の状態のボタンを強調する。確認ダイアログは出さない（何度でも押し直せるため）
- ボタンの下に「最終更新: 12 分前」。30 分以上たっていたら「更新してください」と目立たせる
- 下半分で説明文と画像 URL を編集できる（`PUT /manage/booths/:id`。他の項目は今の値をそのまま送る）

### 7.2 バックエンドの追加: 混雑度の更新時刻

混雑度は Redis（`congestion_status:{id}`）にあり、更新時刻を持っていない。

- 混雑度を更新するとき、同時に `congestion_updated_at:{id}` に UNIX 時刻を保存する
- ブースの取得 API（一覧・個別）の応答に `congestion_updated_at`（ISO 8601、未更新なら `null`）を追加する
- 来場者向けの画面は追加された項目を無視するので影響しない

## 8. 段階 3: 学生会（Gakuseikai）

### 8.1 当日運営 `/manage/ops`

1 画面にタブで 3 つ並べる。

- **混雑度の監視**: 全ブースを「最終更新が古い順」に並べる。30 分以上更新が無いブースは赤で強調。
  各ブースの混雑度をその場で変えられる（担当者の代わりに更新するため）
- **ライブ**: ライブの一覧（開始時刻順）。各ライブに「開演前／公演中／終了」の切り替えボタン（`PATCH /manage/lives/:id/status`）。
  ライブの追加・削除は Admin のみ API で許されている。編集は API では学生会にも許されている（`docs/permissions.md`）が、画面では追加・編集・削除を Admin にだけ表示する
  （2026-10-05 追記）公演中にすると、他の公演中は終了にする（現在のライブを 1 つに保つ）
- **お知らせ**: 現在のお知らせを表示し、書き換えて保存する（`PUT /manage/announcements`）

### 8.2 注意

- お知らせはバックエンドのメモリにしか無く、サーバーを再起動すると消える。消えても問題ないと本人確認済み（2026-10-05）。永続化はしない

## 9. エラー時の表示

- API が止まっているとき: 画面全体を 500 にせず「サーバーに接続できません。時間をおいて再度お試しください」と表示する（来場者画面と同じ方針）
- 保存に失敗したとき: 入力内容を残したまま、その場でエラーを表示する
- 403: 「この操作の権限がありません」
